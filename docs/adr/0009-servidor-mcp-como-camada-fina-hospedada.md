# Servidor MCP como camada fina hospedada

O LPData expõe suas operações de gerenciamento a agentes por um servidor MCP montado na própria aplicação Rails, em `/mcp`, com o transporte Streamable HTTP da gem oficial `mcp`. Não há pacote instalável nem servidor stdio: o LPData é um serviço hospedado, e o MCP dele mora junto do serviço, de modo que o usuário adiciona uma URL e a credencial ao seu cliente. Isso não contradiz a [ADR 0005](0005-aplicacao-exclusivamente-api.md): o endpoint responde JSON-RPC, não HTML, e a apresentação continua fora do LPData.

O servidor é uma camada fina: uma ferramenta por operação que já existe, sem inteligência própria. Ele não valida, não corrige, não transforma e não orquestra o Documento de Conteúdo — a entrada é o mesmo JSON que a API já espera, e o erro do model é repassado inteiro, com o caminho do campo que o Rails já produz. `ContentDocumentValidator` e a [ADR 0006](0006-contrato-do-documento-de-conteudo.md) seguem sendo a única fonte de verdade do contrato; o que o servidor MCP acrescenta é uma cópia desse contrato nas descrições das ferramentas, que é o que substitui o agente ler documentação escrita para humanos. As ferramentas chamam os models diretamente, e o que carrega regra e não pode divergir entre as duas superfícies — o filtro de atributos de Landing Page e a serialização de Asset — vive em objetos compartilhados pelos controllers e pelas ferramentas.

A identificação acontece no Rails, antes do transporte: o cliente envia `X-LPData-Email` e `X-LPData-Password` em toda requisição, verificados pelo mesmo caminho do `sign_in`, e o usuário autenticado chega às ferramentas por `ActiveSupport::CurrentAttributes`. Nenhuma ferramenta recebe credencial como argumento e nenhum token é devolvido ao agente; não existem ferramentas de login, logout ou refresh. Isso corrige a previsão da [ADR 0008](0008-acesso-pelo-navegador-restrito-ao-dashboard.md), que esperava que a integração MCP usasse um token Bearer: o que ela decide continua valendo, porque `/mcp` não recebe nenhuma permissão de CORS e portanto segue inalcançável pelo navegador de outra origem. O resultado da verificação é guardado por sessão MCP em `Rails.cache`, sob uma chave que cobre a própria credencial, para pagar bcrypt uma vez por sessão sem que o cache jamais dispense a checagem de identidade.

O transporte guarda estado de sessão em memória, o que exige que o endpoint seja servido por um único processo. `config/puma.rb` não declara `workers`, então isso está satisfeito hoje; adicionar workers ou instâncias exige migrar para o modo stateless da gem.

Assets não trafegam pelo MCP. Um servidor remoto não lê o disco de quem chama, e uma imagem real enviada em base64 teria que ser gerada token a token pelo modelo. Em vez disso, `get_asset_upload_command` devolve o comando de shell que o agente executa, em que o próprio shell expande as variáveis de ambiente com a credencial: o modelo escreve o comando, mas nunca vê a senha nem o token.
